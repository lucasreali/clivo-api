When task 4.4 landed, only `historyOf` consulted `RoleAccess`. `GET /api/encounters/{id}` and `POST /api/encounters/{id}/completion` returned the full `RecordSheet` to anyone, so reception could read a practitioner's notes in a SEGREGATED clinic simply by asking for the encounter by id instead of through the history. An automated security review flagged the read-by-id path; the completion path leaks the same way, because its response renders values the caller never supplied.

`EncounterService` now funnels both through one `visibleTo(encounter, viewer)` helper, so `findOne(id, viewer)`, `complete(id, viewer)` and `historyOf(customerId, viewer)` all answer with `encounter.summary()` — no sheet — when the policy denies clinical content.

Two endpoints stay ungated on purpose:

- `open` returns a blank sheet built from the template. There is nothing stored to disclose.
- `fill` echoes the values the caller just submitted, and `Encounter.fill` replaces the whole map rather than merging, so the response cannot contain content the caller did not write.

Whether reception should be allowed to *write* clinical content at all is a separate question. Nothing in the todo specifies write rules per role, so no restriction was invented here; task 6.5 owns the role policy and is the place to decide it.

Test consequence: `EncounterApiTest.twoClinicsGetDifferentSheetsFromTheSameEndpoint` runs unauthenticated, and an unauthenticated caller is treated as `RECEPTION`, so it now sets `role_model` to SINGLE in both clinics. The test is about templates producing different sheets, not about roles. `EncounterFixture` gained `reopen(...)` and `completeAsPractitioner(...)` so the clinical tests read as the practitioner acting.
