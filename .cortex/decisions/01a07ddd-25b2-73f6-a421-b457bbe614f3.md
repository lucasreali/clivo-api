The odontogram used to reach the client as nothing but a `List<String>` of 32 tooth codes in `SheetField.options`, which is not enough to draw a chart.

`SheetField` now carries a `ComponentDescriptor` (common/extension), null for ordinary fields: `component`, `groupings` (the ordered layout axes), `regions` (`ComponentRegion`: code, label, `groups` map keyed by the declared groupings, position within the group, `parts`) and `vocabulary` (`ComponentMark`: code, label, rendering). Nothing in it is dental — the odontogram declares `groupings = ["arch","quadrant"]` and BodyMap declares none, so both special components answer the same contract. `FieldDefinition.renderedAs(descriptor, values)` builds it; `renderedWith(values)` still serves plain field types unchanged, so RecordFactoryExtensionTest keeps passing.

The anatomy and vocabulary are data, not code. `V20__component_chart_catalogue.sql` adds `component_chart` (one row per component+variant, holding groupings and regions as JSONB) and `component_mark` (one row per condition). Odontogram seeds `permanent` (32 teeth) and `deciduous` (20 teeth); a template picks between them with `{"variant":"deciduous"}` in the field's `validation` bag, read through the new generic `FieldDefinition.setting(String)` — dentition is component configuration, not a second component. A clinic that wants a condition the catalogue lacks INSERTs a `component_mark` row, the same no-recompile criterion the parameter catalogue satisfies for strategies.

A recorded value is now a list of markings `[{region, part?, mark, note?}]` instead of a region→note map. `MarkedRegions` enforces: the region must be in the declared set, the part must belong to that region, the mark must be in the vocabulary; several markings on different parts of one region are allowed. The core still stores the value as opaque JSON and only asks the component whether it accepted it.

Rejected: teaching `RecordEngine`/`Encounter` about teeth (the whole point of the extension point); one row per tooth in the catalogue (the tooth set is fixed anatomy, so a JSONB document per chart is fewer moving parts, while the open vocabulary stays row-oriented); tenant-scoped catalogue rows (the module/parameter catalogues are global too).

`SpecialComponentTest` moved from `core/encounter` to `patterns/factory` so that a grep for dental vocabulary under `core/` and `configuration/` is empty in tests as well as production code.
