springdoc names a component schema after the simple class name and keeps a single definition per name. Two view records sharing a simple name therefore collapse into one schema, and whichever loses is documented with the other's shape — silently, with no build error and no warning in the document.

This was found by the frontend after `pnpm generate-api`: `/api/customers/{id}` was typed with the five-field shape nested in `EncounterView` (losing nationalId, phone, email, street, postalCode, status, consented, registeredAt), while `encounter.practitioner` was typed with the top-level practitioner's `licenseNumber` even though the JSON carries `license` — a field that compiles fine on the client and simply arrives undefined at runtime.

Nested view records now carry names of their own, mirroring the domain records they render: `EncounterView.AttendedCustomerView`, `AttendingPractitionerView`, `ProvidedServiceView`. Where two nested records had identical shapes in the same package they were not renamed but merged into one package-level record: `CoverageView` and `StandingAlertView` in core/encounter/internal, shared by EncounterView, EncounterHistoryView and CustomerHistoryView. `core/clinical`'s `AlertView` keeps its name because it genuinely differs (it carries customerId).

Three collisions predated this work and were corrected in the same pass, since half a correct document is not a correct document: `CapabilitiesView.ModuleView`/`ParameterView` became `ActiveModuleView`/`EffectiveParameterView`, and `SessionView.ClinicView` became `SignedInClinicView`. They were mistyping `/api/capabilities` and `/api/session` the same way.

The guard is `ArchitectureTest.noTwoViewsClaimTheSameSchemaName`: ArchUnit imports the production classes and asserts that no two whose simple name ends in `View` share it. It lives in ArchitectureTest rather than OpenApiSpecificationTest because the rule is structural — the collision is invisible in the generated document, which contains only the winner, so it cannot be detected by inspecting the spec. It was verified in the red before being accepted: renaming `SignedInClinicView` back to `ClinicView` fails it with `Found duplicate(s): ["ClinicView"]`.

Side effect worth knowing: with the Capabilities nested record renamed, `configuration/modules/internal/ModuleView` disappeared from the document entirely, revealing that it has had no caller since `ModuleActivationController` was deleted (decision 01a07d0e-ff61) and `PlatformModuleView` replaced it. The name collision had been hiding dead code. It was left in place rather than deleted, since removing production code was not part of the request.

Separately, the rules that lived only in Java are now in the contract, because the client has to validate before sending: `RegionMarking.note` declares `maxLength` 400; the one-marking-per-region-and-part rule is stated in the description of the marking array, since OpenAPI cannot express uniqueness across array items; and `appliesTo` semantics are described on both `ComponentMark.appliesTo` and `RegionMarking.parts`. The 400 has a single source, `RegionMarking.NOTE_LIMIT`, read by both the annotation and `MarkedRegions`; it used to be two literals free to drift.

`@Schema(requiredMode = REQUIRED)` on a record component is silently ignored by the model converter used here — the `description` on the same annotation is honoured, which makes the omission easy to miss. `region` and `mark` are therefore marked required explicitly in `RecordValueSchema`, on the copy it builds. That customizer also copies rather than mutates the schema handed back by `ModelConverters.getInstance()`, which is a global singleton cache shared across the JVM.
