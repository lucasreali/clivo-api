Tenant isolation and auditing had to be proven against a real table, but no table in the physical schema carries the full four-column audit trail, and adding one would mean editing `V1__schema.sql`, which is a fixed input of the project.

Fixtures therefore live outside the production migrations: `src/test/resources/db/fixture/V900__sample_entity.sql` creates `sample_entity` (`tenant_id` plus the four audit columns), and `src/test/resources/application-test.yaml` appends `classpath:db/fixture` to `spring.flyway.locations` for the `test` profile only. The production databases never see the file, since `dev` and `docker` keep the single `classpath:db/migration` location.

`out-of-order: true` is set for the same profile: fixtures are numbered V900 so they sort after the real migrations, which would make any future `V3` migration arrive out of order in an already-migrated test database.

The matching `SampleEntity` is a test source in `com.example.clivoapi.common`, extending `AuditableEntity`. Because Spring's entity scan covers the test classpath, `sample_entity` must exist in every test that boots JPA — which is why the fixture location is attached to the whole `test` profile rather than to individual test classes. `DatabaseTest` holds the shared plumbing (one `EntityManager` per tenant binding, since Hibernate reads the tenant identifier when the session opens, not per query) and deletes the fixture rows after each test.
