Two decisions taken while building 6.2.

1. The physical schema shipped `product` without any stock column — on-hand would have to be re-derived from `stock_movement` on every read. That contradicts `Product.isBelowMinimum()` and `Product.decreaseStock(quantity)` living on the entity (the todo names both), and would put a sum-over-movements query in front of every answer. `V8__product_on_hand.sql` adds `on_hand NUMERIC(10,2) NOT NULL DEFAULT 0 CHECK (on_hand >= 0)`. `stock_movement` stays the audit trail; `product.on_hand` is the answer. Movement type is applied polymorphically (`StockMovementType.applyTo(product, quantity)`) so no switch lands in `InventoryService`.

2. The write-off path: `StockDispenser` + `SuppliesUsed` are declared in `common/extension`; `core/encounter` holds `EncounterSupplies` over `List<StockDispenser>` and exposes `EncounterService.useSupplies(...)`, with `Encounter.consume(productId, quantity)` refusing a closed encounter. The HTTP endpoint `POST /api/encounters/{id}/supplies` deliberately lives in `modules/inventory/internal/SupplyController` annotated `@RequiresModule("inventory")`, not in core — that keeps every module code string out of core and still gives the 404-no-trace behaviour. `InventoryStockDispenser` re-checks `ModuleActivationState` because bean presence is deployment-wide while activation is per clinic: a clinic without the module gets no stock movement even if something calls the port.

Authorship is enforced, not optional: `InventoryService` reads `AuditorAware` and refuses a movement with no identified user, matching `stock_movement.recorded_by NOT NULL`.
