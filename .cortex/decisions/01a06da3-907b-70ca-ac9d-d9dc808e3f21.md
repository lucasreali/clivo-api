The `availability` table has no exclusion constraint — unlike `appointment`, which carries `EXCLUDE USING gist`. Overlap between a practitioner's own periods is therefore a pure code rule, and it lives in `WeeklySchedule`, a first-class collection of `AvailabilityPeriod` that refuses to exist while any two of its periods collide. `Practitioner.follow(WeeklySchedule)` replaces the whole week at once, so there is no incremental "add one slot" path where a partial state could slip past the check.

Consequences:
- Building a `WeeklySchedule` throws `BusinessException` (422) before anything reaches the database. The message names the offending period, e.g. `availability MONDAY 08:00-12:00 overlaps another period of the same practitioner`.
- `WeeklySchedule` also sorts its periods into week order on construction, so a schedule always reads back in the order a human expects regardless of the order it arrived in. No `@OrderBy` on the association.
- `TimeRange` is an `@Embeddable` record over `start_time`/`end_time` treating the range as `[start, end)`; it refuses a range that does not end after it starts, mirroring the table's `CHECK (end_time > start_time)`.

`Weekday` wraps the `SMALLINT 0..6` column with the convention **0 = MONDAY .. 6 = SUNDAY** (`DayOfWeek.getValue() - 1`). The HTTP API speaks `DayOfWeek` names, never the number.

Not mapped on `Practitioner`: `user_id` and `specialty_id`. Hibernate's `validate` only checks mapped state, so unmapped columns are harmless. `user_id` is deliberately deferred — linking a practitioner to an `AppUser` would mean reaching into `core/access/internal` from `core/practitioner`, and phase 4.4 is the first task that actually needs the link. There is no `AvailabilitySlotRepository` either: slots are persisted through the `Practitioner` aggregate by cascade.
