The customer history screen aggregates data owned by three places: encounters (core/encounter), invoices (core/billing) and insurance memberships (modules/insurance). core/encounter composes them through two ports declared in common/extension instead of reading the other owners' repositories.

ChargeLedger answers "the financial state of these encounters": chargesOf(List<UUID> encounterIds) returns EncounterCharges, a first-class collection of EncounterCharge (state, net, paid, outstanding, coverage name) that also totals paid and outstanding for the financial summary. Implemented by core/billing/internal/InvoiceChargeLedger, delegating to BillingService.chargesOf, which derives the state from Invoice (NO_CHARGE when no invoice exists, COVERED when a third-party coverage zeroes the net, PAID when nothing is outstanding, OUTSTANDING otherwise). No duplicate status is stored.

CoverageDirectory answers "who covers this customer": coverageOf(UUID customerId) returns Optional<CoverageNote>. Implemented by modules/insurance/internal/InsuranceCoverageDirectory, which returns empty when the insurance module is not active for the clinic — the same runtime activation check InsuranceInvoiceAdjuster already uses. core/encounter injects List<CoverageDirectory> behind CoverageDirectories, so a clinic without the module produces no insurance field at all rather than a null.

core/encounter never learns what an Invoice or an InsurancePlan is; allowedDependencies were not widened and ArchitectureTest's "the core does not know the modules" rule still holds.

Role filtering is applied once, server-side, in core/encounter/ClinicalDisclosure, which asks the existing RoleAccess/RoleAccessPolicy strategy (the role_model parameter) whether the viewer may see clinical content. Clinical record, attachments and clinical alerts are omitted from the response — absent, not blanked — when it says no. No second visibility mechanism was introduced.
