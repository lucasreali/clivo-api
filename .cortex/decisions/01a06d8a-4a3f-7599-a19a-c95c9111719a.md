The physical schema (`V1__schema.sql`) ships `module.code VARCHAR(4)` seeded with `M01`..`M07`. Every module code in `todo.md` (`dependent`, `sessionpackage`, `inventory`, `batch`, `insurance`, `notification`, `commission`) is longer than four characters, and `@RequiresModule("INVT")` would read as an abbreviation, which the project's code standards forbid.

`V3__readable_module_codes.sql` widens `module.code`, `module.requires_module`, `tenant_module.module_code`, `parameter.module_code`, `record_template.requires_module` and `template_field.requires_module` to `VARCHAR(20)`, then renames the seeded rows in place. Renaming a referenced primary key needs the two foreign keys that hold data (`module_requires_module_fkey`, `parameter_module_code_fkey`) dropped and re-added around the UPDATEs; the other three referencing tables are empty at migration time so they need nothing.

The seeded catalog is kept as data, not replaced: names and descriptions stay in Portuguese because they are user-facing labels the project authored, and no module or parameter rows are inserted. The only value changed is `reschedule_window_hours`, moved from the seeded 0..72 to the 1..168 range `todo.md` specifies for task 1.5.

Same migration drops `template_field_field_type_check`. The CHECK pinned `field_type` to a fixed list, which contradicts the reuse criterion of tasks 1.6/4.2 ("the type is a string precisely so a new type needs no recompile") and would block `ReuseTest` from storing a field type invented inside the test. Validating an unknown field type is deferred to 4.2, where the field factories exist to resolve it.
