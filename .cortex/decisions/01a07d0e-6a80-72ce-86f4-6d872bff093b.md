A module endpoint is now reachable only when both hold: the platform activated the module for the clinic, and the clinic manager granted that module to that user.

Status codes are deliberately distinct and must not be collapsed. Module not active for the clinic gives 404, so a clinic never learns a feature it did not contract exists. Module active but no grant gives 403 with "access to module X was not granted", because the feature exists and this person may not use it, mirroring how role-based denial already behaves.

Both gates are evaluated in the single RequiresModuleInterceptor in common/extension, in that order: requireActive then requireGranted. No second interceptor was added.

The grant belongs to access control, not to the module catalog: entity ModuleGrant and service ModuleAccessService live in core/access, table module_grant (migration V17), one row per user per module. No groups or profiles - the product does not need them. A feature module never learns grants exist.

Because common may not depend on core, the interceptor and CapabilityService read grants through the port ModuleGrantState in common/extension, implemented by core/access/internal/GrantedModuleAccess, which resolves the caller from the SecurityContext. An absent principal is treated as not granted (fail closed); Spring Security already refuses anonymous requests to these paths.

Rules on the grant itself: only a MANAGER manages grants and only for users of their own clinic (a foreign user id is 404); granting a module the clinic does not have is 404; a MANAGER always reaches every module active in their clinic and that access cannot be revoked (422), so a clinic cannot lock itself out.

The capability endpoint now reports what the caller can actually reach, not merely what the clinic has.
