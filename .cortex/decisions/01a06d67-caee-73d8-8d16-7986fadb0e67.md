The application is split into five Spring Modulith modules, each declared by an annotated `package-info.java` under `com.example.clivoapi`:

- `common` — `@ApplicationModule(type = OPEN)`, so its nested packages (`tenant`, `audit`, `exception`, later `extension`) stay reachable from everywhere and it is excluded from cycle detection.
- `configuration` and `core` — `allowedDependencies = "common"`.
- `patterns` — `allowedDependencies = { "common", "core", "configuration" }`.
- `modules` — `allowedDependencies = { "common", "core", "configuration", "patterns" }`.

The direction was chosen to keep the graph acyclic, and it has a consequence for the pattern tasks. `ModularityTest` fails on cycles between CLOSED modules, so the plan's literal wording — declaring `AppointmentValidator` inside `patterns/chain` — cannot work: `SchedulingService` in `core` would inject `List<AppointmentValidator>` while the validators reference `Appointment` from `core`, closing a cycle. The same applies to `ExpiredBatchPolicy` between `patterns` and `modules`.

The resolution, which is also the plan's own stated principle, is to declare the *interfaces* in `common/extension` and keep only the *implementations* in `patterns/chain`, `patterns/factory` and `patterns/strategy`. Injecting `List<Interface>` or `Map<String, Interface>` still gives the reuse property the assignment asks for: a new rule is a new class and nothing else.

`ModularityTest` runs `ApplicationModules.of(ClivoApiApplication.class).verify()` and writes the module documentation with `Documenter` into `build/spring-modulith-docs`. Compiling against `Documenter` required promoting `spring-modulith-docs` from `runtimeOnly` to `testImplementation` in `build.gradle.kts`.
