Two related fixes from the authorization audit.

Financial data in a module. Role enforcement existed only in BillingService.reportOf and EncounterService, so the commission module - rates, monthly statements, period closing - was readable and writable by ASSISTANT and RECEPTION even with role_model SEGREGATED, which restricts the core financial report to MANAGER. CommissionService now calls FinancialAccess.requireReporting() on chargeAt, rates, statementOf, close and findOne. accrueFor is deliberately not guarded: it runs from the encounter-completion listener, not from a person.

Because modules/ may not depend on core :: access, the check goes through the port FinancialAccess in common/extension, implemented by core/access/internal/CallerFinancialAccess, which resolves the caller's role from the SecurityContext and delegates to the existing RoleAccess. allowedDependencies was not widened.

Role promotion. AccessService.changeRole and AccessService.deactivate are restricted to a MANAGER acting on a user of their own clinic; a user id from another clinic answers 404 (findByIdAndClinicId). Role.canAssign delegates to the existing canCreate, so a MANAGER may assign RECEPTION, PRACTITIONER, ASSISTANT or MANAGER and never PLATFORM_ADMIN (403).

The last-manager rule is one business method on AppUser, canLeaveManagement(ManagementQuorum), used by both changeRoleTo and deactivate; ManagementQuorum wraps the count of active managers of the clinic. Leaving management as the last active manager is refused with 422, a domain invariant like the closed-clinic rule, not an authorization denial. Note the rule did not previously exist for deactivation either - AppUser.deactivate() was dead code with no caller and no endpoint.
