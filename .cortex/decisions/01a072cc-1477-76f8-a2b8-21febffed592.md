`modules` is a single Spring Modulith module (`modules/package-info.java`); every feature module of phase 6 is a nested package inside it, not a module of its own — mirroring how `patterns` holds chain/factory/strategy.

Declaring `allowedDependencies = "core"` is not enough: Modulith only exposes a module's base package, so `core.customer.Customer` counted as a non-exposed type and `ModularityTest` failed as soon as `modules.dependent.Dependent` referenced it. The fix follows the precedent already set for `patterns` (`core :: access`, `core :: practitioner`, `core :: scheduling`): the core sub-package gets a `package-info.java` with `@NamedInterface("<name>")` and `modules/package-info.java` lists `core :: <name>`.

Consequence: each phase 6 task that reaches into a new core area adds its `@NamedInterface` and the matching entry, so the modules-to-core surface stays explicit and reviewable instead of blanket-open. 6.1 opened `core :: customer`.

Rejected: making each feature module its own `@ApplicationModule`, which would multiply package-info files and force named interfaces between sibling feature modules for no gain — the modules do not call each other.
