`AppUser.signsInWith(RawPassword, PasswordHashing)` is the business rule "an active user whose stored hash matches this password may sign in", and it lives in the entity. To keep it there without dragging `org.springframework.security.crypto` into the domain, `core/access` declares the port `PasswordHashing { hash(RawPassword) -> HashedPassword; matches(RawPassword, HashedPassword) -> boolean }`. `EncodedPasswordHashing` in `core/access/internal` implements it over Spring's `PasswordEncoder`, wired to `BCryptPasswordEncoder` in `SecurityConfiguration`.

Swapping BCrypt for Argon2 is one bean definition; nothing in the domain moves.

`RawPassword` and `HashedPassword` are records whose `toString()` returns `********`, so a password cannot reach a log through an accidental interpolation.

Session mechanics: `SecurityConfiguration` registers an `HttpSessionSecurityContextRepository` and `SessionController.open` follows Spring Security's explicit-save pattern — set the context on `SecurityContextHolder`, then `contexts.saveContext(...)`. The same method writes the clinic id into `TenantResolutionFilter.TENANT_SESSION_ATTRIBUTE`, which is how a sign-in ends up scoping every later request (phase 0.3). Unauthenticated requests answer 401 via `HttpStatusEntryPoint`; `POST /api/session`, `/error` and the springdoc paths are the only public ones.
