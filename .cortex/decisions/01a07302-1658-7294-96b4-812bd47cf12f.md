The phase 7.3 scenarios (src/test/java/com/example/clivoapi/scenarios/) run against a PostgreSQL 16 container instead of the developer's local `clivo_test` database, so the acceptance suite of the project can be replayed anywhere.

The container is a `@Bean @ServiceConnection PostgreSQLContainer<?>` in `ScenarioDatabase`, imported by the abstract `ScenarioTest`. Spring Boot starts and stops it with the application context, and the context cache keeps a single container for the five scenario classes. This was chosen over `@Testcontainers`/`@Container` static fields, which would restart the container per class, and over `@DynamicPropertySource`, which duplicates what `@ServiceConnection` already derives.

The remaining tests (phases 0-6) still use the local Postgres named by the `test` profile — importing `ScenarioDatabase` is what forks a second, container-backed context, and that import is deliberately confined to the scenarios package.

Scenario methods are named `ctNN_whatTheScenarioProves()`: the number cross-references the project's written test-case suite, the rest stays English like the rest of the code. `ct01`-`ct03` tenant isolation, `ct04`-`ct05` invalid configuration, `ct06`-`ct09` agenda, `ct10`-`ct12` record template, `ct13`-`ct14` expired batch.
