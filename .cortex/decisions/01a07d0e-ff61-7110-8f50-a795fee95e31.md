An authorization audit found that ModuleActivationController (configuration/modules/internal) exposed PUT and DELETE /api/modules/{code}/activation with no role restriction. SecurityConfiguration gates only POST /api/users to MANAGER and leaves everything else at anyRequest().authenticated(), so any clinic user of any role - RECEPTION included - could contract a module for their own clinic. Combined with the absence of role checks inside the modules, a receptionist could activate the commission module and then read every practitioner's earnings.

Its GET /api/modules also listed the whole catalog with an active flag, telling a clinic about features it never contracted, against the project rule that a module the clinic did not contract must leave no trace.

The controller was deleted rather than restricted. Restricting it to MANAGER would have left the manager able to self-contract any module, which makes the platform-activation gate decorative. Activation now happens only through PlatformClinicModuleController under /api/platform/tenants/{id}/modules, and a clinic discovers what it has through /api/capabilities. The dependency-refusal coverage that lived in ModuleActivationApiTest moved to PlatformApiTest.

The audit cleared the other checks: every controller under modules/ carries a class-level @RequiresModule; every extension-point adapter re-checks activation before delegating; all module entities are tenant-scoped so a foreign identifier simply misses; the capability endpoint cannot name an inactive module; and /api/platform/** is 404 for anyone who is not PLATFORM_ADMIN.
