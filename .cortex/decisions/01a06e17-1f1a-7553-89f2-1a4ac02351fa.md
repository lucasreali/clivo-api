`appointment` and `schedule_block` store `starts_at`/`ends_at` as `TIMESTAMPTZ`, and `ux_appointment_no_overlap` is an `EXCLUDE USING gist` over `tstzrange(starts_at, ends_at)`. Changing the columns to `TIMESTAMP` would mean dropping and rebuilding that constraint, so the physical schema was left untouched.

Hibernate cannot bind a `LocalDateTime` to a `TIMESTAMP_UTC` column: `@JdbcTypeCode(SqlTypes.TIMESTAMP_UTC)` on a `LocalDateTime` field passes schema validation but fails at insert with "Could not convert 'java.time.LocalDateTime' to 'java.time.Instant'". So `common/time/TimeWindow` is a record of two `Instant` components (`startsAt`, `endsAt`) and every domain method speaks `LocalDateTime`, converting through a single `CLINIC_OFFSET = ZoneOffset.UTC` constant. `TimeWindow.of(start, end)` and `TimeWindow.wholeDay(day)` are the only entry points; the raw constructor is only used by Hibernate.

Consequence: a 09:00 appointment is stored as 09:00Z. Clinic times are wall-clock, the whole application reads them back through the same offset, and the exclusion constraint compares stored values, so scheduling stays correct. Raw SQL that applies a session timezone would misread these columns.

Derived repository queries follow the record components, hence names like `findByPeriodStartsAtLessThanAndPeriodEndsAtGreaterThanOrderByPeriodStartsAtAsc` taking `Instant` parameters.
