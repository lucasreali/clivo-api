The todo asked for `AppointmentValidator` in `patterns/chain`, but `core` only allows a dependency on `common`, so `SchedulingService` cannot see a type declared in `patterns`. The interfaces and their payloads therefore live in `common/extension` — `AppointmentValidator` + `AppointmentProposal`, `ModuleActivationValidator` + `ModuleActivationProposal` + `ActivationIntent` — and only the links live in `patterns/chain`: `AvailabilityValidator` (10), `ScheduleBlockValidator` (20), `OverlapValidator` (30), `RescheduleWindowValidator` (40), `ModuleDependencyValidator` (10), `ExistingDataValidator` (20).

`@Order` values are spaced by ten so a new link can be inserted between two existing ones without touching them; each link exposes its value as a `public static final int ORDER` so tests can position a new link relatively.

For the links to reach core and configuration behaviour, `core.scheduling`, `core.practitioner` and `configuration.modules` were annotated `@NamedInterface`, and `patterns` declares `allowedDependencies = { "common", "core :: practitioner", "core :: scheduling", "configuration :: modules" }`. Without the named interfaces those sub-packages are internal to their module and `ModularityTest` fails. The `internal` sub-packages stay hidden because a named interface does not extend to sub-packages.

`SchedulingService` and `ModuleActivationService` inject `List<...Validator>` and wrap it in a first-class collection (`AppointmentValidation`, `ModuleActivationValidation`); no link holds a reference to the next one, and neither service keeps any inline copy of the rules the chain owns.
