A PLATFORM_ADMIN has tenant_id null but must still configure a specific clinic. That scope is explicit and authorized, never a free-form header.

Where it lives. The prompt offered common/tenant or a nested package under configuration. Both are closed: ArchitectureTest.theSharedPortsDependOnNoOneElse forbids common from seeing core or configuration, and a package under configuration inherits allowedDependencies = "common", so neither could reach AccessService to create the first manager. Routing all of it through common/extension ports would have invented three ports for a module that is not an extension point. Instead there is a new top-level module com.example.clivoapi.platform declaring its own allowedDependencies = {common, core :: access, configuration :: modules, configuration :: parameter} - the same shape patterns and modules already use, and no widening of any existing module. This required adding @NamedInterface("parameter") to configuration/parameter; nothing outside configuration referenced that package before.

Clinic CRUD itself (TenantService) stayed in common/tenant, since it needs nothing but Tenant and TenantRepository. platform holds only the orchestration (ClinicOnboarding) and the web layer.

How the scope is bound. PlatformAccessInterceptor guards /api/platform/** and throws ResourceNotFoundException (404) for any caller that is not PLATFORM_ADMIN - the same no-trace rule as RequiresModuleInterceptor. Deliberately not a hasRole() matcher in SecurityConfiguration, which would answer 403 and confirm the endpoint exists. PlatformClinicScopeInterceptor then runs on /api/platform/tenants/{tenantId}/** , reads the URI template variable, loads the clinic and binds TenantContext; afterCompletion clears it. The platform module and parameter endpoints therefore reuse ModuleActivationService and ClinicParameterService unchanged - only the entry point differs.

Who may create whom. Role.canCreate(Role) owns the matrix (PLATFORM_ADMIN creates PLATFORM_ADMIN; MANAGER creates any clinic role; RECEPTION, PRACTITIONER and ASSISTANT create nobody). AppUser.canCreate delegates to it and AppUser.create(UserRegistration, PasswordHashing) is what actually builds the new user, so the new account always inherits the caller's own clinic - a MANAGER cannot place a user in another clinic even by crafting the body, and cannot ask for PLATFORM_ADMIN. AccessService.register loads the caller from AuditorAware and calls that method; the role in the request is validated, never used as-is. POST /api/users dropped PLATFORM_ADMIN from its security matcher; platform administrators are created at POST /api/platform/administrators.

Provisioning. ClinicOnboarding.open creates the Tenant and its first MANAGER in one transaction and activates no modules. It seeds no parameter rows: ParameterSettings.valueOf already falls back to ParameterDefinition.defaultValue when a clinic has no row, so seeding would write rows that change nothing and would then have to be kept in step with the catalog.

Tenant gained the lifecycle it lacked: activate(), deactivate(reason) and close(reason) on an embedded TenantLifecycle value object (status, status_reason, status_changed_at - migration V12__tenant_lifecycle.sql). A clinic is never deleted. The code is validated and upper-cased in TenantRegistration, is unique across the platform and is mapped updatable = false.
