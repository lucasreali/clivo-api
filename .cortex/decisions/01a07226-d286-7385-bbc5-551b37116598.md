`core/encounter` maps `encounter.record_template_id` as a plain `Long` column (`updatable = false`) instead of a `@ManyToOne` to `RecordTemplate`.

Reason: the Spring Modulith boundary declares `core` with `allowedDependencies = "common"`, so `core` must not import `configuration`. A JPA association to `RecordTemplate` would break `ModularityTest`. The foreign key still exists in the physical schema; only the object graph is cut.

This costs nothing in behaviour: `RecordTemplateService.redefine` on a published template creates a *new row* (`nextVersionAfter`), so the stored id already pins name and version. Reopening a completed encounter therefore returns the record in the version it was filled with, which is task 4.1's acceptance criterion.

The encounter exposes the pair (templateId, values) as `RecordFilling` — a value object in `common/extension` — which is also the argument the `RecordAssembly` port takes to render the sheet.

`signed_by` and `dependent_id` are left unmapped for now: signing is not part of phase 4 and dependents arrive in 6.1. Both columns are nullable, so `ddl-auto: validate` is unaffected.
