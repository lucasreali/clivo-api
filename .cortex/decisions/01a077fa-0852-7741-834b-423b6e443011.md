`V1__schema.sql` has always carried an `audit_log` table — tenant, user, entity name, record id, action, `old_value`/`new_value` as JSONB, `occurred_at` — and no Java code touched it at all. Spring Data auditing (`AuditableEntity`, `AuthenticatedAuditor`) only fills last-changed columns on a few tables; it never produces a previous/new value pair, so the trail was unreadable because it was also unwritten.

Added, all read-only:

- `common/audit/AuditEntry` — `@Entity` on `audit_log`, extends `TenantScopedEntity` so `@TenantId` scopes every query. Exposes `snapshot()`, no getters.
- `common/audit/AuditedRecord` — `@Embeddable` value object over (`entity`, `record_id`); it is also the query parameter, so the repository method is `findByRecordOrderByOccurredAtDesc(AuditedRecord)`.
- `common/audit/ValueChange` — `@Embeddable` over the two JSONB maps.
- `common/audit/AuditAction` — CREATE, UPDATE, DEACTIVATE, ACCESS, mirroring the column's CHECK constraint.
- `common/audit/internal/AuditLogRepository`, `common/audit/AuditTrail` (service), `core/billing/internal/AuditTrailController` + `AuditEntryView` at `GET /api/audit-trail?entity=&recordId=`.

The controller sits under `core/billing/internal` beside the financial report rather than in a new module; `common` may not depend on `core`, so the entity stores `user_id` as a plain `Long` and never references `AppUser`.

The write side was deliberately NOT added. Recording a row on every encounter fill would leave `audit_log` rows referencing `app_user` and `tenant`, and `DatabaseTest.discardTestData` deletes both without deleting `audit_log` first — the whole suite would fail on a foreign key. Fixing that means either editing the test fixture or relaxing those foreign keys to `ON DELETE CASCADE` in a new migration. Until one of those happens, `/api/audit-trail` answers correctly over an empty table.
