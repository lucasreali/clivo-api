Six decisions taken together so the encounter sheet screen (odontogram) can be drawn from the contract alone, all confirmed by the product owner before implementation.

1. A marking is a named type. `RegionMarking(region, parts, mark, note)` and the first-class collection `RegionMarkings` live in common/extension; `RegionMarkings.in(Object)` is the single place that knows the stored JSON shape and is used by both patterns/factory (validation) and core/encounter (the provenance fold). The old package-private `Marking` map wrapper is gone. `SheetField.value` and `RecordFillingRequest.values` stay `Object`/`Map` in Java — the core still stores opaque JSON — but the OpenAPI union declares the value shapes. Rationale for declaring a union rather than leaving `{}`: the union enumerates JSON value shapes (string, number, RegionMarking[]), not field types, so a new field type reuses a shape and the extension promise of decision 01a07235 is intact. BOOLEAN, MULTI_CHOICE and ATTACHMENT are in the template_field CHECK but have no factory; when they land the union gains `boolean` and `string[]`.

2. `part: String` became `parts: List<String>`. Absent or empty means the region as a whole; a list means one clinical fact spanning those faces (one marking, one note). "All faces" is the explicit full list — no `"*"` wildcard, because the descriptor already names the faces and a wildcard would need a decoder on both sides. `(region, part)` may not repeat inside one field value (422), otherwise provenance identity is ambiguous. Consequence accepted: one mark per face, so a transient state replaces a condition rather than coexisting with it.

3. Provenance is incremental and resolved server-side. A session records only what it changed; `MarkingProvenance` folds the customer's completed encounters in chronological order plus the open draft, keyed by `MarkedPart(region, part)`, latest wins. `SheetField` gained `markings: List<MarkedRegionState>`, each with `origin{source SESSION|HISTORY, since, recordedAt, encounterId, practitionerName}`; `since` is the start of the unbroken run of the same mark, which is what gives "canal tratado em 12/2024". `value` still holds exactly what this session wrote, so the PUT round-trips; the duplication between `value` and `markings` is deliberate (one is for saving, the other for drawing). core/encounter learns nothing dental: it folds over fields where `descriptor != null`, and the shape parser lives in common/extension. Provenance is resolved for a single encounter read only, never in listCustomerEncounters, where it would be O(N^2) — that path uses `ClinicalDisclosure.listedFor`.

4. Comparison is one operation with one parameter: `GET /api/encounters/{id}/record/comparison?asOf=<date-time>` (compareEncounterRecord), inclusive, baseline from COMPLETED encounters only. Chosen over `?against=<encounterId>` because under the incremental fold the state is a function of time, not of an encounter, and `asOf` subsumes the encounter case (pass its completedAt) while the reverse does not hold. `date-time` rather than `date` so two encounters on the same day are not ambiguous. Required, no default: a default baseline of "the previous encounter" would silently differ per patient.

5. `component_mark` gained `applies_to` (REGION | PART | ANY), enforced by `MarkTarget`. Values are descriptor vocabulary, not dental vocabulary, so BODY_MAP (regions with no parts) is all REGION. Odontogram: higido, ausente, extracao_indicada, canal, coroa, protese, implante = REGION; carie, restaurado, selante = PART; fratura = ANY. This stops "an absent face", which means nothing. `em_tratamento` was deliberately NOT added: "in treatment in this session" is derived from provenance (source SESSION), not a vocabulary entry. Only `selante` is new.

6. Validation split by question, not by moment. `Field.accept(values)` checks shape/vocabulary/target/duplication/note length and runs on `PUT /record` as well as on completion; `Field.check(values)` adds required-field presence and runs only on completion. A draft must accept incomplete work; it must not accept malformed work. `accept` is a DEFAULT method on `Field` so a field type defined outside production code (ReuseTest, RecordFactoryExtensionTest) keeps compiling untouched — making it abstract broke exactly the tests that prove the extension point, which was the signal the first shape was wrong.

Also: `encounter.signed_by` existed in V1 and was never written or exposed; completing an encounter now signs it with the authenticated user (through the existing AccessService.signedIn, reached from EncounterCompletion so EncounterService keeps its collaborator count). New column `encounter.last_saved_at`, written by `fill()` — a domain fact like started_at/completed_at, not AuditableEntity, which would require created_at/created_by columns the table lacks.

`EncounterView` went from 12 flat components to nested customer/practitioner/service/signedBy, the same shape in all three outputs (GET /{id}, PUT /record, POST /completion), matching the already-composed CustomerHistoryView. Room was deliberately left out of the domain: a room that is only a header label carries no rule; if rooms matter they matter for scheduling conflicts, which is a separate feature.

V21 also transforms stored `field_values` from `part` to `parts` in JSONB rather than reseeding — V15 already set the precedent of transforming recorded data, and a completed record is signed clinical data that cannot be discarded on a schema change even in a demo environment. The transform was verified against PostgreSQL 18 before being committed: it touches only rows matching `$.*[*].part`, preserves array order, and leaves scalars and empty arrays alone.
