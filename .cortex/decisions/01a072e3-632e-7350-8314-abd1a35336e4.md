6.7 introduces the invoice adjustment extension point the todo asks for: `InvoiceAdjuster`, `InvoiceAdjustment(coverage, reduction, reason)` and `BillableEncounter` in `common/extension`; `BillingService` injects `List<InvoiceAdjuster>` behind the `InvoiceAdjustments` collaborator and applies them while issuing, before the invoice is saved. The insurance percentage therefore reaches the invoice without `core/billing` naming the insurance module. `InvoiceAdjustment.coverage` is a string resolved by `InvoiceCoverage.of(...)` — the enum stays core vocabulary and the module never imports it.

Note the split with 6.6: the session package sets coverage AFTER issue (a completion listener calling `coverByPackage`), insurance adjusts DURING issue (an adjuster). That is deliberate — the package's decision depends on consuming a session, which must happen against a persisted invoice, while insurance is a pure function of the customer and the gross amount.

Schema: `customer_insurance` shipped with a composite primary key `(customer_id, insurance_plan_id)` and no id column, the only table in the schema without a surrogate key. Mapping it would have required an `@IdClass` with a non-record helper class purely for JPA. `V9__customer_insurance_identity.sql` drops that primary key, adds `id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`, and keeps the pair unique through `ux_customer_insurance` — same guarantee, entity shaped like every other one.
