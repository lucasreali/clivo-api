The Abstract Factory in `patterns/factory` resolves a `FieldFactory` by the bean name that equals the `fieldType` string stored in `template_field`. `FieldCatalog` injects `Map<String, FieldFactory>` and looks the type up; there is no enum, no switch and no registry to edit.

Adding a field type therefore means writing one `@Component("MY_TYPE")` class implementing `FieldFactory` (plus its `Field` product). `RecordFactoryExtensionTest` proves it: the test declares `@Bean("EMOJI_SCALE")` inside a `@TestConfiguration` and the engine renders and validates it without a single production file changing.

Two consequences worth knowing:

- Registering the same factory under a second name must go through `@Qualifier` on the alias `@Bean` method (`BuiltInFieldTypes`). Injecting the concrete factory type instead fails with `NoUniqueBeanDefinitionException`, because the alias bean has that same concrete type. Aliases in place: LONG_TEXT to SHORT_TEXT, DECIMAL and SCALE to INTEGER.
- A type with no factory is refused at render time with a `BusinessException` naming the field and the type. It is a deliberate refusal, not a silent skip: `template_field`'s CHECK on `field_type` was dropped in V3, so the database accepts any string and the engine is the only place that can complain.

`FieldDefinition` wraps `FieldContent` (one instance variable) and carries the shared behaviour every product needs: presence check, option list, `validation` rule lookup, rendering and the `refusal(...)` message factory. Products stay tiny and hold only the definition.

The port `core` talks to is `RecordAssembly` in `common/extension` (`assemble` renders, `validate` checks), implemented by `RecordEngine`. That is what keeps `core` free of any `patterns` or `configuration` import.
