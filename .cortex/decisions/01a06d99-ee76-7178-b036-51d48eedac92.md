`app_user`'s unique index is `ux_app_user_email ON app_user (COALESCE(tenant_id, 0), lower(email))` — an email is unique *within* a clinic, not across the platform. The same person can therefore hold accounts in two clinics with one address, and email alone is not an identifier.

`POST /api/session` takes `{clinic, email, password}`. `SignInAttempt.clinic()` is an `Optional<String>` over the clinic code: present, `AccessService` looks the user up with `findByClinicCodeAndEmail`; absent, it looks up `findByClinicIsNullAndEmail`, which by the schema CHECK can only be a `PLATFORM_ADMIN`. One row either way, no ambiguity to resolve at runtime.

Rejected: looking up by email alone and disambiguating when several rows come back. That turns a login into a multi-step negotiation and leaks which clinics an address exists in.

Emails are normalised to lower case by the `EmailAddress` value object so Java-side lookups agree with the `lower(email)` index.

Failure is `InvalidCredentialsException` -> 401, handled by `AccessExceptionHandler` inside `core/access/internal` rather than by `common`'s `ApiExceptionHandler`, so the credentials vocabulary stays inside the access module. The message never distinguishes an unknown email from a wrong password from an inactive user.
