`tenant_module` and `tenant_parameter` have composite primary keys `(tenant_id, module_code)` and `(tenant_id, parameter_code)`. Rather than mapping them with `@IdClass` or `@EmbeddedId`, `ModuleActivation` and `ClinicParameter` extend `TenantScopedEntity` and declare only the business code as `@Id`; the tenant column stays the inherited `@TenantId` field.

This works because a Hibernate session is bound to a single tenant (`RequestTenantIdentifierResolver` resolves it when the session opens), so the JPA identity is unique within any session, and Hibernate adds the tenant restriction to both queries and identifier loads. `ddl-auto: validate` checks columns and types, not that the JPA identifier matches the physical primary key, so the mapping validates.

Two consequences to keep in mind. First, an assigned identifier makes `JpaRepository.save` take the `merge` path (SELECT then INSERT) for a row that does not exist yet; that is correct but means the returned instance is the managed one. Second, repositories deliberately expose derived finders (`findByModuleCode`, `findByParameterCode`) instead of `findById`, so identifier lookups go through HQL where tenant filtering is unambiguous. `ModuleActivationServiceTest.activationOfOneClinicDoesNotReachTheOther` and `ClinicParameterServiceTest.valueOfOneClinicDoesNotReachTheOther` prove the isolation.
