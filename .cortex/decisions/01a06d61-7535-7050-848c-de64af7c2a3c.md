Tenant isolation is enforced by Hibernate discriminator multi-tenancy, never by hand-written `where tenant_id = ?`. `TenantScopedEntity` is a `@MappedSuperclass` carrying `@TenantId Long tenantId` mapped to `tenant_id`; Hibernate enables its `_tenantId` filter on every query and fills the column on insert. `TenantContext` (a bean holding a ThreadLocal) is populated per request by `TenantResolutionFilter` from the `tenantId` HTTP session attribute and cleared in a `finally`. `RequestTenantIdentifierResolver` is wired into Hibernate through a `HibernatePropertiesCustomizer` setting `MULTI_TENANT_IDENTIFIER_RESOLVER`.

Two constraints shaped this:

1. `@TenantId` must sit on a basic single-column attribute (Hibernate's `TenantIdBinder` rejects associations), so the field is a `Long`, not a `Tenant` association.
2. Hibernate 7 throws `HibernateException: SessionFactory configured for multi-tenancy, but no tenant identifier specified` when the resolver returns null, so returning null is not an option.

When nothing is bound the resolver returns the sentinel `0L` instead of null, and `isRoot` stays false: unbound sessions filter on `tenant_id = 0` and therefore reach no row, while inserts fail on the foreign key. Fail-closed was chosen over the alternative of declaring the sentinel a "root" tenant (which disables the filter entirely and would silently expose every clinic whenever the context failed to bind). Cross-tenant access for `PLATFORM_ADMIN` must therefore be added explicitly later rather than falling out of a missing binding. The sentinel `0` matches the schema's own convention (`COALESCE(tenant_id, 0)` in the unique indexes) and cannot collide with a real id, since `tenant.id` is `GENERATED ALWAYS AS IDENTITY` starting at 1.

`TenantIsolationTest` pins all three behaviours: two clinics do not see each other's rows, an entity keeps the tenant it was created in, and a session with no tenant bound reaches nothing.
