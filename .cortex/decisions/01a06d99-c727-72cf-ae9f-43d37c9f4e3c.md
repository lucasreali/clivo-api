Every other tenant-owned entity extends `TenantScopedEntity`, which carries Hibernate's `@TenantId` and lets the discriminator filter every query (decision of phase 0.3). `AppUser` deliberately does not.

Two reasons make `@TenantId` unusable here:
- `app_user.tenant_id` is nullable. The schema's CHECK `((user_role = 'PLATFORM_ADMIN') = (tenant_id IS NULL))` says a platform administrator belongs to no clinic, while `TenantScopedEntity` declares the column `nullable = false` and `RequestTenantIdentifierResolver` substitutes `0L` when nothing is bound — which would insert a dangling FK.
- Sign-in happens *before* a tenant is bound. `TenantResolutionFilter` reads the clinic from the HTTP session, and the session only exists after a successful sign-in. A `@TenantId` filter would hide the very row the login needs to read.

So `AppUser` maps the clinic as `@ManyToOne(fetch = LAZY) @JoinColumn(name = "tenant_id") Tenant clinic`, nullable, and the entity itself enforces the CHECK in `requireClinicMatching` so the refusal is a 422 with a readable message instead of a constraint violation.

Consequence: queries over `app_user` are never filtered automatically. Any listing must scope itself explicitly — `AccessService.usersOfCurrentClinic` reads `TenantContext` and calls `findByClinicIdOrderByNameAsc`. Reviewers of new `AppUserRepository` methods must check this by hand; the discriminator will not save them.
