The module names, parameter names and chart vocabulary seeded by V1, V4 and V20 were in Portuguese and surfaced verbatim in the front end (the clinic settings screen shows `parameter.name`, the odontogram shows `component_mark.label`). The product is now English end to end, so this data had to follow.

Chosen approach: a new migration, `V22__english_reference_data.sql`, that UPDATEs the rows. The already-applied migrations keep their Portuguese literals so Flyway checksums stay valid — an existing database just applies V22, a fresh one applies V1 in Portuguese and V22 translates it. Rewriting V1/V4/V20 in place was rejected because it forces every existing database to be dropped or repaired. V3, which renamed the module codes M01…M07, is the precedent for this style.

What V22 changes:
- `module.name` / `module.description` and `parameter.name` to English.
- `component_mark.label` and `component_mark.code` to English (higido→healthy, carie→caries, restaurado→restored, ausente→missing, extracao_indicada→extraction_indicated, fratura→fracture, canal→root_canal, coroa→crown, implante→implant, protese→prosthesis, selante→sealant, dor→pain, edema→swelling, hematoma→bruising, cicatriz→scar, limitacao→limited_movement).
- The two tooth surfaces still in Portuguese: palatina→palatal, oclusal→occlusal.

Because condition codes and surfaces travel inside markings already written, V22 rewrites `component_chart.regions` and `encounter.field_values` in the same migration with temporary SQL functions, the way V21 did. The catalogue and the records are therefore renamed together and no stored marking is orphaned.

`seed/seed.sql` and `seed/CREDENTIALS.md` were translated as well, including template field codes (dor_escala→pain_scale, regiao→region, evolucao→progress, …), because the seed truncates and rebuilds and is self-consistent. Proper nouns were left alone: people's names, street addresses, Brazilian council registrations (CREFITO/CRM/CRO/CRMV), insurer brands, and CPF/CNPJ values.

Test fixtures that named the old codes or surfaces were renamed with them (SpecialComponentTest, MarkingProvenanceTest and the inventory/batch fixtures). The suite was NOT run to confirm this: no JDK is installed in the WSL shell where the change was made. It was validated instead by applying V1…V22 plus the seed to a scratch database and inspecting the result.

Running order after pulling this: start the API so Flyway applies V22, then re-run `seed/seed.sql`.
